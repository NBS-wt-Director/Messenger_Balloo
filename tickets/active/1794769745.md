## Дефекты, вскрытые прогоном (все три — исполнением, не чтением)

### 1. Экран чата не открывался: `getMessages` ждал массив, сервер отдаёт страницу

Замер живым запросом:

```
GET /api/chats/:id/messages → 200 {"messages":[…],"pagination":{"hasMore":false,…}}
```

`ChatViewScreen` делал `messagesData.map(...)` → `TypeError` → `catch` →
`navigate('/chat')`. Хэш возвращался с `#/chat/<id>` на `#/chat` через ~1 с.
**Практически: чат нельзя было открыть ни в одном браузере**, поэтому realtime
проверить было нечем — этим и объяснялось «не увидел в другом окне».

- Правка: `packages/web/src/services/api.ts` — `getMessages` нормализует форму
  ответа (`Array.isArray(res) ? res : res?.messages ?? []`).
- Попутно: `ChatViewScreen` в `catch` сверялся с устаревшим `chats` из замыкания
  рендера → теперь `useChatStore.getState().chats`.
- Тест: `packages/web/src/__tests__/services/api.messages.test.ts` (4 кейса).
  Доказательство нефиктивности: с снятой нормализацией — `Tests: 3 failed | 288 passed`.

### 2. `ws-token` и `refresh-cookie` сжигали лимит входа

`applyRateLimit` относил к `authLimiter` (5/мин) всё, что начинается с
`/api/auth/`, включая служебные `GET /api/auth/ws-token` и
`POST /api/auth/refresh-cookie`. React StrictMode дублирует эффект, поэтому
одна вкладка = 2 refresh + 2 ws-token; **две вкладки с двумя аккаунтами
выжигали лимит, и второй вход падал с 429** «Слишком много попыток
авторизации» — при том что пароль никто не подбирал.

- Правка: `packages/server/src/middleware/rateLimit.ts` — эти два пути уходят
  в общий `apiLimiter` (100/15мин); строгий лимит остаётся на login/register/2fa.
- Тест: `packages/server/src/__tests__/middleware-ratelimit.test.ts`
  «обслуживание сессии … не сжигает лимит входа». Доказательство нефиктивности:
  с снятой правкой — `✕ … Tests: 1 failed, 9 passed`.

### 3. Время сообщения рисовалось как «Invalid Date»

Сервер отдаёт `createdAt` **секундами unix в строке** (`BigInt` → строка в
`app.ts`); `new Date("1794768916")` → `Invalid Date`. В пузыре было видно
`Invalid Datetwo-window-…`.

- Правка: `MessageBubble.tsx`, `MessageListVirtual.tsx` — `new Date(Number(x) * 1000)`,
  как в остальных 15+ экранах (`ArchiveScreen`, `ChannelViewScreen`, `SupportScreen`…).
- Тест: `MessageBubble.test.tsx` → блок «время сообщения в форме реального API»
  (2 кейса). Прежний набор мокал `createdAt: 1700000000000` (мс числом) и время
  не проверял — поэтому дефект был зелёным. Доказательство нефиктивности:
  с снятой правкой — `× … Tests: 2 failed | 291 passed`.

## Отдельно зафиксировано, НЕ исправлено

`[auth] Failed to persist refresh token to DB: The provided value for the column
is too long for the column's type` — `generateTokens` пишет
`familyId = crypto.randomUUID()` (36 симв.) в `RefreshToken.familyId
@db.VarChar(25)` (`packages/shared/prisma/schema.prisma:1338`). Ошибка
проглатывается `try/catch`, поэтому вход работает, но **А-02 (семейный отзыв
refresh-токенов) не работает никогда** — в `refresh_tokens` не записывается ни
одна строка. Нужна миграция (`VarChar(25)` → `VarChar(64)`/`Text`) или
короткий familyId. В этот тикет не брала: это правка схемы + миграция, а не
точечная, и требует отдельного прогона миграций на прод-подобной БД.
