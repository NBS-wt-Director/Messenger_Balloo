## Риск №2 (найден локальным прогоном 31.10.2026): миграция падает на данных прода

**Это блокирующий риск, важнее самого отставания образа.** Если выполнить батч F
«как есть», контейнер `balloo-server` **не запустится**, а БД останется в
состоянии `P3009` (failed migration), из которого `migrate deploy` больше не идёт.

**Причина.** Цепочка миграций противоречива:

| Миграция | Что делает с FK `reports.targetId → users.id` |
|---|---|
| `20260817000000_initial` | **создаёт** (строка 1261) |
| `20260907000000_report_target_no_fk` | **удаляет** (уже применена на проде) |
| `20261010000000_add_missing_columns` | **снова создаёт** (строка 41) |
| `20261016000100_drop_reports_target_fk` | **снова удаляет** |

Между «создать» и «удалить» миграция обязана проверить **все** существующие
строки `reports`. А `reportController.ts:17-18` (тот же код и в `bcf8643`) пишет
жалобу на сообщение как `targetId = messageId`, `targetType = 'message'` — то есть
`targetId` **не является `users.id`**. Такой строке FK не находится → ошибка.

**Воспроизведение (локально, на копии прод-состояния, 31.10.2026):**

```text
# 1) БД приведена к состоянию прода: 2 миграции + данные
users=2 chats=1 messages=1 reports=1     # reports: targetType='message', targetId=<id сообщения>
# 2) прогон остатка цепочки
Migration name: 20261010000000_add_missing_columns
Database error code: 23503
Database error:
ERROR: insert or update on table "reports" violates foreign key constraint "reports_targetId_fkey"
DETAIL: Key (targetId)=(m_test_1) is not present in table "users".
EXIT=1
# 3) повторный прогон — БД заблокирована:
Error: P3009
migrate found failed migrations in the target database, new migrations will not be applied.
The `20261010000000_add_missing_columns` migration started at ... failed
EXIT=1
```

**Контрольные прогоны (чтобы исключить ложную тревогу):**

- на **пустой** БД вся цепочка из 15 миграций применяется: `All migrations have
  been successfully applied.` (EXIT=0) — значит дело именно в данных;
- упавшая миграция **транзакционна**: после сбоя `feedbacks` не создана,
  `support_messages.ticketId` остался `character varying`, FK `reports_targetId_fkey`
  отсутствует, число таблиц 55 (не изменилось). То есть данные не испорчены —
  но запись о сбое в `_prisma_migrations` **остаётся** и блокирует повтор.

**Вероятность на проде — не «теоретическая».** FK на `reports.targetId` был снят
ещё 07.09 (`20260907000000`, применена — она вторая в БД), а бэкенд с 21.09
пишет жалобы на сообщения. Если хотя бы одна такая жалоба есть — миграция упадёт.
**Точный ответ даёт только запрос к прод-БД** (read-only, батч D ниже).

### Рабочая гипотеза провала (не доказана — доказывает F1c)

Хост резолвит `binaries.prisma.sh` **только на IPv6** и ходит по IPv6 (п.1 дал
HTTP-ответ). Docker-сеть `bridge` по умолчанию IPv6 **не имеет**
(`daemon.json`/`ip_ipv6` не включались), поэтому контейнер сборки получает имя
без маршрута → `ETIMEDOUT`. `registry.npmjs.org` при этом жив, т.к. у него есть
IPv4-записи. Отсюда: лечение — сборка в хостовой сети (`--network=host`), а не
смена зеркала и не ротация чего-либо.

Варианты (цена/риск), если гипотеза подтвердится:

| Вариант | Что делает | Цена | Риск |
|---|---|---|---|
| (а′) `docker build --network=host` | сборка тем же `Dockerfile.server` в хостовой сети; тег `balloo/server:local` | минуты, правок репо нет | контейнер сборки видит хостовые порты (в Dockerfile их нет — только apt/npm/prisma); обратимо |
| (б) `PRISMA_ENGINES_MIRROR` на npmmirror | правка `Dockerfile.server` (один `ARG`) + коммит | минуты + коммит | меняет репозиторий ради сетевой проблемы хоста; mirror — сторонний источник бинарников |
| (в) собрать у меня → `docker save` → `docker load` | полностью обходит блокировку | трансфер ~1,5–2G руками владельца | расхождение слоёв/версий, долгая пересылка |

| п.4 `npx prisma` без правок ×2 | **`EXIT=124` ×2** | не падение, а **зависание** дольше 90 с |
| п.5 то же с `--dns-result-order=ipv4first` ×2 | **`EXIT=124` ×2** | лечение **не работает** (ожидаемо: IPv4 уже первые) |
| п.6 прод | аптайм тот же | не тронут |
| п.3 (из F1″) `docker build --network bridge` | `network mode "bridge" not supported by buildkit` | **факт:** в buildkit допустимы только `default`/`host`/`none` |

### Что это меняет

1. **DNS не при чём.** `dns.lookup` уже отдаёт IPv4 первыми, `autoSelectFamily=true`,
   `--dns-result-order=ipv4first` не помогает. Гипотеза №2 закрыта фактом.
2. **Симптом — зависание (`EXIT=124`), а не `ETIMEDOUT`.** В F1″ с `</dev/null`
   процесс успевал упасть по сети за <70 с, в F1⁗ с `--yes` висит дольше 90 с.
   То есть поведение **нестабильно по времени**, и ретраи Prisma
   (`RETRIES_COUNT = 2`, `minTimeout 1000`, `factor 2`,
   `chunk-NJSUFXSP.js:8036-8093`) растягивают это до десятков минут — отсюда
   «24 минуты тишины» в F1′.
3. **Мои проверки шли не в той среде.** `curl` 8/8 я гоняла в
   `balloo/server:rollback-20261101` (там есть `openssl` + `ca-certificates`,
   `Dockerfile.server:50`), а `npx` — в чистом `node:22-slim` **без** CA и openssl
   (отсюда и `Please manually install OpenSSL`). Это **разные условия**, и вывод
   «сеть стабильна» к среде сборки прямо не относится.

### Единственный оставшийся подозреваемый: сеть **buildkit** ≠ сеть `docker run`

Все мои 8/8 успешных GET были в `docker run`. Сборка идёт в **отдельном netns
buildkit** (п.3 выше доказал, что это другая сеть с своими правилами). Плюс
слой, на котором виснет сборка (`#32`, prod-стадия `12/17`), выполняется **после**
установки `openssl`+`ca-certificates` (`3/17`), то есть в тех же условиях, что мой
успешный `curl`. Значит CA-версия тоже не объясняет.

### Как это объясняет все прошлые прогоны

- **F1 / F1″**: падение на `schema-engine.sha256` — первый же TLS-handshake к
  Cloudflare. Размер файла (103 байта) значения не имеет, отсюда «падает на
  крошечном файле».
- **F1′ (24 минуты тишины)**: `npx` скачивает пакет, потом postinstall `@prisma/engines`
  висит на TLS, ретраи (`RETRIES_COUNT = 2`, `factor 2`) растягивают это.
- **F1c/F1‴ (curl 8/8 OK)**: `curl` этой несовместимости не подвержен — мои

- **F1⁵ (`PROBE_EXIT=0`)**: `time: not found` + пайп — батч был холостым.
- **F1⁶ не нужен**: причина доказана локально, гонять владельца не требуется.

### Побочные факты, снятые прогоном

- `packages/*/package.json` не фиксируют версию node: `engines` в корне
  `>=20.0.0` — **любая** 22.x подходит, поэтому `node:22-slim` молча приехал
  на OpenSSL 3.5.
- `Dockerfile.web:2` тоже `node:22-slim` — **тот же риск**: в `Dockerfile.web:31`
  есть `npx prisma generate`, он упадёт так же, если слой не в кэше. Проверка
  веб-сборки входит в план.
- `.dockerignore` **не исключает** `.android-sdk` (2,8G), `.cypress-cache` (817M),
  `.check` (48M), `tmp` (2M) — в контекст сборки уходит **2,6G** лишнего
  (`du -sh` без `node_modules`/`.git`/`.android-sdk`... на сервере было `68M`,
  потому что там этих каталогов нет). На прод-сборку это не влияет, но на моей
  машине контекст раздувается.

## Решение: pin базового образа на `node:22.19-slim` (OpenSSL 3.0.17)

**Рекомендую pin, а не `--tls-max-v1.2`:**

- pin убирает причину (OpenSSL 3.5), а не симптом; TLS 1.2-ограничение останется
  в конфиге навсегда и будет неявно ослаблять все исходящие соединения;
- `engines: >=20.0.0` соблюдён (22.19 ≥ 20);
- `22.19-slim` — последний образ до смены OpenSSL, `prisma generate` и
  `npm install -g prisma` на нём дали `EXIT=0` (прогон выше);
- правка — две строки в `docker/Dockerfile.server` (строки 2 и 44) и две в
  `docker/Dockerfile.web` (строка 2 — builder; nginx-стейджи не трогаются),
  плюс `--tls-max-v1.2` **не нужен**.

Оговорка по риску, которую фиксирую честно: `node:22.19` — не «самая свежая» 22.x,
обновления безопасности 22.20+ не приедут. Альтернатива, если владелец предпочтёт
свежий node: `ENV NODE_OPTIONS=--tls-max-v1.2` (тоже проверено, `EXIT=0`), с
осознанным решением ограничить исходящий TLS 1.2.

### План работ (после решения владельца)

1. Правка `docker/Dockerfile.server` + `docker/Dockerfile.web` (pin 22.19) — коммит.
2. **Локальная сборка** `compose build server` на моей машине (docker есть,
   `x86_64`, база та же) — доказательство, что образ собирается с нуля.
3. `git push` → на сервере `git fetch && git checkout -B main origin/main`.
4. Повтор **F1** (`compose build server`) — с новым базовым образом.
5. Дальше по очереди: F2 (прогон миграций на копии БД), F3, G, приёмка.

**Стоп-условие:** без решения владельца (pin 22.19 против `--tls-max-v1.2`)
правки в `Dockerfile` не вношу — это изменение продакшен-сборки.
