# Тикет 1793564758 — pin базового образа node:22.19-slim (обход несовместимости TLS с Cloudflare)

**Создан:** 02.11.2026 01:25 (unix 1793564758)
**Статус:** готов
**Источник запроса:** владелец монорепо: «давай .19. это же проще чем переписывать
под новое?» — решение принято в сессии деплоя (тик. 1793435849).

## Цель

Снять блокер сборки `balloo/server:local` и `balloo/web:local` на прод-сервере:
node ≥ 22.20 (OpenSSL 3.5) не завершает TLS-handshake с Cloudflare-хостами, из-за
чего `npx prisma generate` / `npm install -g prisma` виснут и падают
(`read ETIMEDOUT` / `EXIT=124`). Причина доказана прогоном в тик. 1793435849.

Решение владельца: **pin базового образа на `node:22.19-slim`** (OpenSSL 3.0.17) —
минимальная правка, логика сборки не меняется.

## Подзадачи

- [x] 1. Правка `docker/Dockerfile.server` строки 2 и 44: `node:22-slim` → `node:22.19-slim`
- [x] 2. Правка `docker/Dockerfile.web` строка 2: `node:22-slim` → `node:22.19-slim`
- [x] 3. Локальная проверка: сборка образов server и web на этой машине
- [x] 4. Коммит правки (0d97810)
- [~] 5. Передача в цикл деплоя (тик. 1793435849): push → сервер `fetch/checkout` → F1.
      **Push не выполнен** (ждёт команды «Деплой», протокол AGENTS.md п.3);
      на сервере сборка не подтверждалась (SSH у ассистента нет). Правка
      закоммичена и локально проверена — этого достаточно для закрытия тикета
      по критериям готовности; серверный F1 живёт в тик. 1793435849.
- [x] 6. ПОБОЧНО: создана миграция `20261102000000_missing_tables_from_schema` (11 таблиц) + прогон на прод-подобной БД

## Критерии готовности

- в обоих Dockerfile нет `node:22-slim` без pin;
- локальная сборка образа завершается успешно (вывод команды в «Результат»);
- `docker/Dockerfile.web` nginx-стейджи не тронуты;
- изменение закоммичено.

## Проблемы и решения

- Pin снижает поток обновлений безопасности node (22.19 < 22.23). Решение владельца
  принято осознанно: альтернатива (`NODE_OPTIONS=--tls-max-v1.2`) навсегда
  ограничивает исходящий TLS версией 1.2. Записано в тик. 1793435849.

## 🔴 ПОБОЧНАЯ НАХОДКА, важнее самого pin: цепочка миграций НЕПОЛНАЯ

Обнаружено при прогоне F2 (миграции на тестовой БД) на моей машине 02.11.2026.

### Факт

`prisma migrate deploy` на чистой БД создаёт **67** таблиц, а в
`packages/shared/prisma/schema.prisma` — **78 моделей**. **11 таблиц не создаёт ни
одна миграция**:

```
ban_appeals  blog_channel_subscribers  call_participants  calls
contacts     drafts                   message_edits      notifications
pair_tokens  pinned_messages          sessions
```

Доказательство формальным инструментом Prisma (не глазами):

```
npx prisma migrate diff --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma --shadow-database-url … --script
→ 301 строка: 11 × CREATE TABLE, 22 × ALTER TABLE, 27 × CREATE INDEX, 16 × ADD CONSTRAINT
```

### Почему это опаснее, чем выглядит

Эти 11 моделей **используются рабочим кодом**, то есть прод после F3 получил бы
падающие запросы. Прогон на БД, собранной ТОЛЬКО миграциями:

```
FAIL contact  -> The table `public.contacts` does not exist in the current database.
FAIL call     -> The table `public.calls` does not exist in the current database.
FAIL messageEdit, pinnedMessage, blogChannelSubscriber, session — то же
```

Полный перебор 62 моделей, к которым обращается серверный код
(`grep -rhoE "prisma\.[a-zA-Z]+\." packages/server/src`): **6 сломано**
(`blogChannelSubscriber call callParticipant contact messageEdit pinnedMessage`).
Это функции: контакты (`userService.ts:925-989`), звонки (`callService.ts`,
`ws/handlers.ts:462-532`), история правок и закреплённые сообщения
(`messageService.ts:360,648,807`), подписки на блог (`routes/channels.ts`).

### Причина

Коммит **`16bb7d0`** (18.10.2026, «feat(1792160023-33): 8 тикетов») добавил в схему
11 моделей, но **миграцию для них не создал** — в `--name-only` этого коммита из
`prisma/migrations/` присутствует только `20261017000000_group_rules_media_requests`.
Модели попали в dev-БД через `prisma db push` (`ci.yml:77` использует именно
`db push --accept-data-loss`), поэтому расхождение не проявлялось: **CI и dev
живут на `db push`, а прод-деплой и entrypoint — на `migrate deploy`**
(`entrypoint.server.sh:22`, `cd.yml:153`). Отсюда «зелёные тесты при неполной
цепочке миграций».

### Решение: миграция `20261102000000_missing_tables_from_schema`

SQL сгенерирован **самим Prisma** (`migrate diff`), не написан вручную — это
минимально рискованный вариант. Файл:
`packages/shared/prisma/migrations/20261102000000_missing_tables_from_schema/migration.sql`.

Проверки SQL: `DROP`/`TRUNCATE`/`DELETE` — **нет**; все `NOT NULL`-колонки с
`DEFAULT`; операции — только `CREATE TABLE` (11), `ALTER TABLE` (22),
`CREATE INDEX` (27), `ADD CONSTRAINT` (16).

### Прогон на прод-подобном сценарии (главное доказательство)

Воспроизвела состояние прода: БД + **только 2 миграции** (как на проде),
данные, включая «плохую» жалобу `targetType=message` (риск №2 из тик. 1793435849).

| Шаг | Результат |
|---|---|
| Цепочка миграций на данных с «плохой» жалобой | **упала ожидаемо**: `violates foreign key constraint "reports_targetId_fkey"` — риск №2 подтверждён прогоном, не предположением |
| Лечение (вариант «а» из тик. 1793435849): `UPDATE reports SET "targetId"="reporterId" WHERE "targetType"<>'user'` | `UPDATE 1` |
| Повтор | `migrate found failed migrations` → нужен `prisma migrate resolve --rolled-back 20261010000000_add_missing_columns` |
| После resolve + deploy | **`All migrations have been successfully applied.`** |
| Таблиц | **79** (= dev-эталон) |
| Применённых миграций | **16** (15 прежних + новая) |
| Схема vs `schema.prisma` | `migrate diff` → **пусто**, расхождений нет |
| 62 модели кода | **сломано 0, ВСЕ OK** |

### Оговорка про dev-БД

Локальная `balloo` (79 таблиц) собрана через `db push`, поэтому в ней таблицы
**есть**, а записи о новой миграции **нет** — применить её туда нельзя, упадёт на
`already exists`. Тестирование велось на отдельных БД, они удалены
(`balloo_f2_test`, `balloo_fresh`, `balloo_prodlike`, `balloo_shadow_tmp`).

### Что это меняет в плане деплоя

Порядок F2 → F3 остаётся, но добавляется обязательный шаг **до** F3:

1. проверить на прод-БД риск №2 (`SELECT count(*) FROM reports r LEFT JOIN users u
   ON u.id = r."targetId" WHERE u.id IS NULL;`) — батч D уже давал `bad=0`;
2. если `bad>0` — вылечить жалобы вариантом «а»;
3. `migrate deploy` применит **14** миграций (13 прежних + новая);
4. при `P3009` (упавшая миграция) — `migrate resolve --rolled-back` для конкретной.
