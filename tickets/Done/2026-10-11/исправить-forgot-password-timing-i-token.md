# исправить-forgot-password-timing-i-token

**Создана:** 11.10.2026 (из проверочного тикета а-02)
**Приоритет:** средний

## Находка 1 — timing-оракул в `/forgot-password`

`authService.requestPasswordReset`: ветка «email не найден» возвращается сразу
(один `findUnique`), ветка «email найден» делает `deleteMany` + `create` +
**`await sendResetPasswordEmail`** (SMTP = сотни мс). По времени ответа
однозначно различается, зарегистрирован ли email.

Фикс: не ждать отправку письма (`sendResetPasswordEmail(...).catch(...)` —
fire-and-forget, как уже сделано для welcome/verification в `register`), либо
выровнять ветки искусственной задержкой. Первый вариант честнее и проще.

## Находка 2 — токены сброса/верификации хранятся в БД открытым текстом

`verificationToken.token` — сам токен (`randomString(32)` = 256 бит, энтропия
ok), не хеш. Утечка БД = живые ссылки смены пароля до истечения срока.

Фикс (пошагово, с обратной совместимостью):
1. писать новый токен как `sha256(token)` (hex), в email слать сырой токен;
2. при проверке искать `findUnique({ where: { token: sha256(input.token) } })`;
3. переходный период: старые открытые токены принимать по прямому значению
   (второй запрос) до их истечения (15 минут с момента деплоя — ок), потом
   ветку убрать;
4. тест: выпущенный до апгрейда токен работает, выданный после — в БД только
   хешем.

## Критерии готовности

- `grep -n "await sendResetPasswordEmail" authService.ts` → нет await;
- в БД для новых токенов лежит sha256, сброс работает end-to-end (тест);
- `pnpm --filter @balloo/server test` зелёные.

## Результат

**Находка 1 (timing) — исправлено 11.10.2026:** `await sendResetPasswordEmail(...)`
заменён на fire-and-forget (`sendResetPasswordEmail(...).catch(...)`) — как welcome
и verification в `register`. Ветка «email есть» больше не медленнее ветки «email нет»
на время SMTP. Остаточная разница — единичные мс на `deleteMany`+`create` в ветке
«email есть» (в «email нет» их нет); SMTP-масштаба (сотни мс) больше нет. Полное
выравнирование искусственной задержкой не делал — цена выше пользы, а исходный
вектор (замер по сети) убран.

**Находка 2 (sha256 токенов) — исправлено 11.10.2026:** `tokenHash = sha256(token).hex`
(колонка `VarChar(255)` вмещает 64 hex — миграция не нужна). Хранение хешем в:
`requestPasswordReset` (сброс), `register` (email_verification). Поиск по хешу в
`resetPassword`, `verifyEmail`. **Сырого фолбэка нет намеренно**: двойной поиск
хеш→сырой принял бы украденный из БД хеш как валидный токен (дыра хуже исходной).
Незавершённые ссылки на момент деплоя протухают (сброс 15 мин, верификация 24 ч) —
пользователь запросит новую.

Сырой токен уходит только в письмо. Тесты (`auth-service-depth`, `session-revocation`)
переведены на hash-хранение; новый тест full-flow перехватывает письмо через spy и
проверяет, что в БД лежит НЕ сырой токен.

## Доказательство

- `grep -n "await sendResetPasswordEmail" authService.ts` → 0;
- `grep -n "tokenHash" authService.ts` → хелпер + 3 применения (2 записи, 2 поиска);
- тест «сырой токен НЕ лежит в БД» + «вход по новому паролю работает» — зелёные;
- `tsc --noEmit` чисто; **32 набора / 594 теста зелёные дважды подряд**
  (флак от `paymentConfig.deleteMany` в payment-тестах убран переходом на upsert).
