# Тикет 1790480787-01 — P38-0: гостя сбрасывает с публичных страниц на /login

**Создан:** 2026-09-27 08:46 (unix 1790480787)
**Закрыт (локальная часть):** 2026-09-28 09:35
**Статус:** код починен и проверен живым браузером локально; **прод — «не подтверждено»**
до деплоя владельцем (см. п.7)
**Первоисточник:** `tickets/archive/Мультитикет_поддомены_C.md` §7, блок «P38-0»
**Родительский тикет расщепления:** `tickets/active/1790479120.md`, п.8

## Симптом (прод, доказан)

`https://balloo.su/#/blog`, `/#/`, `/#/privacy` у гостя заканчиваются
`hash=/login`. В прогоне `scripts/p37-prod-check.cjs` две строки помечены
`REDIRECT->/login` — это `/` и `/blog`.

## Причина (снимок сетевых запросов, `scripts/p38-prod-redirect-probe.cjs`)

1. `GET https://api.balloo.su/api/users/me` → **401** (гость);
2. `POST /api/auth/refresh-cookie` → **400**, потому что refresh-куки нет вообще
   (`packages/server/src/controllers/authController.ts:206-234`: `if (!refreshToken) → 400`);
3. клиент в ветке «refresh не ок» делает `window.location.hash = '#/login'`
   (`packages/web/src/services/api.ts:64-73`);
4. `AuthProvider` вызывает `api.getMe()` при монтировании на **любом** маршруте,
   включая публичные (`packages/web/src/components/providers/AuthProvider.tsx:54-66`).

**В этой сессии найдена вторая, независимая причина — см. «Причина №2» ниже.**
Одна правка api.ts дефект не закрывала.

## Суть фикса

Различать два состояния:

| Ситуация | Ответ refresh | Что делать |
|---|---|---|
| сессии нет вообще | **400** | URL **не трогать**; решение о входе принимает `ProtectedRoute` (`packages/web/src/router/index.tsx:140-176`) |
| сессия протухла | **401** | редирект на `/#/login` — текущее поведение оставить |

Плюс: публичный маршрут `/` не должен затеняться защищённой группой.

## Причина №2 (найдена в этой сессии, 2026-09-28)

После правки api.ts гость на `/#/` **всё равно** уходил на `#/login`. Диагностика
навигации (`history.pushState/replaceState` + `hashchange` в
`scripts/p38-0-guest-check.cjs`) показала разный источник редиректа:

- на `/#/` — `replaceState → #/login` из недр React Router
  (`completeNavigation → handleLoaders → startNavigation`), то есть
  `<Navigate to="/login" replace />` из `ProtectedRoute` (`router/index.tsx:174`);
- на `/#/blog` и `/#/privacy` до правки api.ts — `hashchange → #/login`,
  то есть присваивание `window.location.hash` в `api.ts`.

Причина: в роутере две записи с `path: '/'` — публичный лендинг
(`router/index.tsx:192-201`) и защищённая группа приложения
(`router/index.tsx:311-322`) с ребёнком `{ index: true, element: <Navigate to="/chat"/> }`.
React Router ранжирует ветку с index-ребром выше простой ветки ` '/' `,
поэтому на URL `/` матчилась защищённая группа, а не лендинг.

Доказательства (не по памяти):

1. Мок-API в режиме «пользователь авторизован»: заход на `http://localhost:5173/#/`
   заканчивается `hash="#/chat"` — значит сработал index-ребро защищённой группы,
   а не лендинг (`scripts/p38-0-shots/authed-root.png`).
2. `matchRoutes(router.routes, '/')` на старом роутере возвращает **2** совпадения
   (группа + index-ребро), на исправленном — **1** (публичный лендинг).
   Тест `router.public-landing.test.ts` на коде HEAD падает с
   `expected [ … ] to have a length of 1 but got 2`.

## Результат

### 1. Код до правки (подтверждение подзадачи 1)

`packages/web/src/services/api.ts:48-74` (HEAD): при `response.status === 401`
выполнялся `POST /api/auth/refresh-cookie`, и **любой** неуспешный ответ
(`else`) либо любое исключение (`catch`) давали
`window.location.hash = '#/login'`.

`packages/server/src/controllers/authController.ts` (`refreshCookie`):
`if (!refreshToken) → 400 { error: 'Bad Request' }`, любые остальные ошибки → 401.
То есть 400 = «куки нет вообще» = гость.

Гипотеза из `tickets/active/1790523936.md` §3.1 («400 даёт CSRF-обёртка»)
**опровергнута**: `packages/server/src/middleware/security.ts:85-108`
(`csrfProtection`) при отсутствии `x-csrf-token` только печатает
`console.warn` и вызывает `next()` — статус не меняет никогда.
400 в этом эндпоинте даёт ровно одна проверка — отсутствие refresh-токена.
Там же: файлов `useSession.ts` и `authLandingPage.ts` в репозитории нет
(`find packages scripts docs -name "*useSession*" -o -name "*authLandingPage*"` — пусто),
ссылки на их строки в том тикете выдуманы предыдущей сессией.

## Проблемы и решения (если возникли)

1. **Правка api.ts оказалась недостаточной.** Первый прогон браузером показал
   `#/login` на `/#/` при исправленном refresh. Причина — ранжирование маршрутов
   React Router (см. «Причина №2»). Решено удалением index-ребра у защищённой
   группы + `GuestRoute` на публичном `/`.
2. **Порт 3100 занят** посторонним процессом (отвечает 404 на
   `/api/auth/refresh-cookie`, к Balloo не относится) — мок-API поднят на 3199,
   web запущен с `VITE_API_URL=http://localhost:3199`. Чужой процесс не трогался.
3. **Гипотеза про CSRF** из тикета `1790523936` не подтвердилась кодом
   (`security.ts:85-108` ничего не блокирует) — записана поправка в тот файл.
